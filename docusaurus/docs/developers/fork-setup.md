# Fork setup

This document explains which values in this repository depend on the
owner of the repository (GitHub or Docker Hub), how the workflows in
`.github/workflows/` resolve them, and what a fork owner has to configure so
that their fork publishes under their own namespace.

## What is automatic

The workflows do not hard-code the repository owner. They derive it from
GitHub's own context:

* `github.repository_owner` is the GitHub username or organization that
  owns the repository in which the workflow is running. In a fork that is
  the fork's owner, never the upstream's.
* `github.repository` is `<owner>/<repo>`, e.g. `VulcanoSoftware/tgdcfs`.

Workflows use these like this:

| Workflow | What is derived |
|---|---|
| `docker-publish.yml` | Docker Hub namespace and GHCR path for the `tgdcfs` and `tgdcfs-fe` images |
| `docker-preview.yml` | Same, for `preview-<commit>` and `preview` tags |
| `release.yml` | Same, for `X.Y.Z` and `X.Y` release tags |
| `test.yml` | Codecov `slug` for the coverage upload |
| `badge-sync.yml` | The owner, repository and default branch in the README badges, and the GitHub Pages and Docker Hub links in the README |
| `gh-pages.yml`, `docker-publish.yml`, `docker-preview.yml` | The Docker images and Pages links shown in the web frontend (config generator and getting-started guide), resolved when it is built |

A fork that runs these workflows therefore publishes to
`<fork-owner>/tgdcfs` and `<fork-owner>/tgdcfs-fe` on Docker Hub, and to
`ghcr.io/<fork-owner>/<fork-repo>/tgdcfs` and `ghcr.io/<fork-owner>/<fork-repo>/tgdcfs-fe` on GHCR,
never to the upstream namespaces.

### GHCR publishing needs no configuration

The GHCR push uses the workflow's own `GITHUB_TOKEN` with the
`packages: write` permission, so every fork publishes its images to its
own GHCR namespace without any secret. A package created this way starts
private; change its visibility to public under the package's *Package
settings* if anonymous pulls are wanted. Docker Hub publishing stays
behind the `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN` secrets: a fork without
them skips Docker Hub with a warning and still ships to GHCR. The config
generator's Docker command panel offers both registries; the images it
suggests are the fork's own. `tgdcfs-gh-pages/next.config.ts` derives them
when the frontend is built, from `GITHUB_REPOSITORY` and
`DOCKERHUB_NAMESPACE` (the same inputs the publishing workflows use),
which the Pages workflow and the `tgdcfs-fe` image build pass in. Nothing
in the frontend sources is rewritten or has to be edited.

### README badges and site links

Markdown is static, so the badges at the top of `README.md` cannot ask
GitHub who owns the repository they live in. The "Sync README badges"
workflow solves this:

1. Everything between the `<!-- badges-start -->` and `<!-- badges-end -->`
   markers in `README.md` is generated by `scripts/sync_badges.py`.
2. On every branch push the workflow regenerates the block from
   `github.repository`, the default branch and the Docker Hub namespace
   (`vars.DOCKERHUB_NAMESPACE` with a fallback to the owner, lowercased
   because Docker Hub namespaces are lowercase).
3. The same script repoints the GitHub Pages URLs and the Docker Hub link
   in the README from the upstream to the fork's own
   (`https://<fork-owner>.github.io/tgdcfs/`). The web frontend is not
   rewritten: it resolves its own Docker images and Pages links at build
   time (see above).
4. When the result differs from what is committed, the workflow commits it
   with `[skip ci]`, so it cannot run against its own commits.

On the upstream the regeneration is byte-identical to what is committed,
so no commit ever appears there. On a fork the first push after forking
rewrites the badges to the fork's own coordinates, and every later push
leaves them alone. Nothing has to be configured for this: it follows the
fork automatically.

## What a fork owner must configure

Docker Hub does not know about GitHub forks. A fork that wants its images
published under its own Docker Hub account needs credentials that GitHub
Actions can use, and the repositories `tgdcfs` and `tgdcfs-fe` must exist
on that Docker Hub account.

### 1. Create the Docker Hub repositories

Log into [hub.docker.com](https://hub.docker.com/) and create the public
repositories:

* `<dockerhub-username>/tgdcfs`
* `<dockerhub-username>/tgdcfs-fe`

They must be named exactly like that; the workflows derive the image name
from the repository name in `pyproject.toml` / the matrix.

### 2. Create a Docker Hub access token

On the same Docker Hub account, open **Account Settings → Personal access
tokens → Generate new token**. Give it `Read & Write` permissions, name it
e.g. `github-actions-tgdcfs`, and copy the value once — Docker Hub shows it
only once.

### 3. Add the secrets to the fork

On the fork, go to **Settings → Secrets and variables → Actions → New
repository secret** and add:

| Name | Value |
|---|---|
| `DOCKERHUB_USERNAME` | The Docker Hub username (not the token name) |
| `DOCKERHUB_TOKEN` | The access token created above |

### 4. Optional: set `DOCKERHUB_NAMESPACE`

By default the workflows use `github.repository_owner` as the Docker Hub
namespace. If the Docker Hub namespace differs from the GitHub username,
add a repository variable instead of editing the workflows:

**Settings → Secrets and variables → Actions → Variables tab → New
repository variable**

| Name | Value |
|---|---|
| `DOCKERHUB_NAMESPACE` | The Docker Hub namespace, e.g. `mydockerhuborg` |

Every workflow that pushes images reads `vars.DOCKERHUB_NAMESPACE` with a
fallback to `github.repository_owner`:

```yaml
DOCKERHUB_NAMESPACE: ${{ vars.DOCKERHUB_NAMESPACE || github.repository_owner }}
```

Set it once and every future merge picks it up automatically.

### 5. Optional: Codecov

`test.yml` uploads coverage to Codecov with `slug: ${{ github.repository }}`,
which is always correct for the fork. If you want coverage to appear on
your Codecov dashboard, add a `CODECOV_TOKEN` repository secret. Without
it, coverage uploads are skipped on branches where they are not required
(`pull_request` and `master`).

## What is deliberately not automatic

* **GitHub Pages itself** must be enabled once per fork: under
  *Settings → Pages*, set the source to *GitHub Actions*. After that the
  "Deploy site to GitHub Pages" workflow (`gh-pages.yml`) publishes the
  Next.js web frontend at `https://<fork-owner>.github.io/tgdcfs/` and,
  under `docs/` in the same artifact, the Docusaurus documentation at
  `https://<fork-owner>.github.io/tgdcfs/docs/`. Both read the fork's own
  coordinates from `github.repository`, so nothing in
  `docusaurus/docusaurus.config.ts` has to be edited.

## Guard against accidental upstream publication

Workflows never reference a hard-coded upstream namespace, so a fork cannot
publish to it by accident: `github.repository_owner` is always the fork's
owner. The only way a fork can publish to the upstream Docker Hub
namespace is by setting `DOCKERHUB_NAMESPACE` to it, which requires write
access to that namespace's Docker Hub credentials and is not something a
regular fork does.

## Summary

| What | Value | Where it comes from |
|---|---|---|
| GitHub owner | `github.repository_owner` | Automatic, per repository |
| Docker Hub namespace | `vars.DOCKERHUB_NAMESPACE \|\| github.repository_owner` | Repository variable, default GitHub owner |
| Docker Hub credentials | `secrets.DOCKERHUB_USERNAME`, `secrets.DOCKERHUB_TOKEN` | Repository secrets, per fork |
| GHCR | `github.repository`, lowercased, with `GITHUB_TOKEN` | Automatic, per repository |
| Docker images in the web frontend | `github.repository`, `vars.DOCKERHUB_NAMESPACE` | Resolved at build time by `next.config.ts` |
| Codecov project | `github.repository` | Automatic |
| README badges | `github.repository` | Regenerated by `badge-sync.yml` |
| Pages site (frontend + docs) | `github.repository` | Automatic, per repository |
